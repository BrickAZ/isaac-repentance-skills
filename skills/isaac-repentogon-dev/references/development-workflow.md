# Development and Migration

## New Project

Discover genuine emptiness, requested identity, game/build, tools and first
mechanic. Required REPENTOGON already chosen remains settled. Missing files do
not permit inventing an existing mod, but do not block an authorized scaffold.

Create only needed bootstrap, portable gate, localized failure feedback, gated
feature modules and real content registrations. Technical module layout can be
selected within scope. Public identity, balance, pools and unlock choices remain
user-owned. Do not import another mod's IDs, saves, resources or assumptions.

## Migration

A future-new-mod preference does not silently alter an existing optional mod.
For an authorized migration record original call sites/formula/ownership/state,
native signature and required fixes, eliminated duplicates, XML loading behavior,
old-save interpretation, and tests. Preserve mechanic semantics when replacing
polling or manual caches with native features. Do not leave two authority stores
or overlapping inventory handlers that pay the same reward twice.

```text
Static, pure and mock checks run; exact limits:

```

Unknown technical facts are Unverified — discovery required. Continue accessible
research; do not ask users to choose signatures or supply facts the agent can find.

## Meaningful Tests

- Gate: absent/non-table, old numbers/suffix, unknown/dev, missing capability,
  supported release, lazy module load and single registration.
- Callbacks: implicit Mod argument, actual owner/filter, return propagation,
  overlap/deduplication, nullable player/source; mocks require source evidence.
- Content: XML parse/paths, runtime name resolution, single stat owner,
  add/remove/re-evaluate, temporary duration, persistence/revival.
- World: invalid context rejection, nil/false placement, empty candidates,
  topology/dimensions, preview RNG/weights, shared-state restoration conflicts.
- UI: build once, unload/reload, title/run/exit, stale references, render purity,
  Chinese display, scale and actual mouse/keyboard/controller behavior.

Select affected tests, expand for changed behavior or failures. Do not mock native
placement or registration as unconditionally successful and call the engine proven.
